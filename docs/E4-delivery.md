# E4: доставка отчёта в Telegram

> Выверено против установленного OpenClaw **2026.8.1** на ноде `lilu` 21.09.2026, а не
> по документации.

## Где живёт эта работа

Не в форке. Отчёт собирает MCP-инструмент `ozon_ad_report`, а расписание и доставка —
задача OpenClaw на проде. Поэтому здесь рансбук, а не код.

## Два предупреждения плана — оба подтвердились

**1. `--best-effort-deliver` гасит сигнал о недоставке.** Справка установленного CLI
говорит дословно: *«Do not fail the job if delivery fails (default: false)»*. То есть с
этим флагом упавшая доставка не делает задачу упавшей, и отчёт перестаёт приходить
молча. По умолчанию флаг выключен — значит его достаточно просто **не передавать**.

🔴 **У всех трёх существующих задач-брифов он стоит.** Замерено:

```
brief_client_8f30ca85…  delivery: {"mode":"announce","channel":"telegram","to":"183866240","bestEffort":true}
brief_client_513b1590…  delivery: {"mode":"announce","channel":"telegram","to":"5457896619","bestEffort":true}
brief_client_9fc220a5…  delivery: {"mode":"announce","channel":"telegram","to":"7349158853","bestEffort":true}
```

Это не наша правка и не часть E4, но знать об этом стоит: если бриф перестанет
приходить, ни один механизм об этом не скажет.

**2. Сверку задач вести только с `--all`.** Замерено: `openclaw cron list` показал 9
строк, `openclaw cron list --all` — 10. Разница ровно одна: выключенная задача. А из
справки `--delete-after-run` следует, что при неудачной обязательной доставке задача
**остаётся выключенной**. То есть отвалившаяся доставка сначала выключает задачу, а
потом задача исчезает из списка — и «всё в порядке» выглядит так же, как «ничего нет».

## Команда заведения

Заведена **выключенной**: задача сама отправляет сообщения владельцу, и включение —
решение владельца, а не следствие выкатки.

```bash
sudo -u openclaws XDG_RUNTIME_DIR=/run/user/1001 openclaw cron add \
  --cron '0 9 * * *' --tz Asia/Tashkent \
  --agent client_513b1590bcb44989b7cbdfe0bc1a63ae \
  --announce --channel telegram --to 5457896619 \
  --display-name 'Ozon: ежедневный отчёт по рекламе' \
  --disabled \
  'Собери отчёт по рекламе Ozon за вчера…'
```

Время — 09:00 по Ташкенту, то есть **07:00 МСК**. Сбор идёт в 03:00 МСК, так что к
отчёту ряд за вчера уже накоплен; утренний бриф в 08:00 Ташкента не задевается.

**Задача заведена и ВКЛЮЧЕНА 21.09.2026** по решению владельца. Идентификатор
`875d1804-dd94-42b1-9fd1-136f20151b59`. Следующий запуск — 22.09 в 09:00 по Ташкенту. Проверено: в `cron list`
без `--all` она не видна, в `delivery` поле `bestEffort` **отсутствует** — то есть
неудачная доставка уронит задачу, как и задумано.

Включение — одной командой:

```bash
sudo -u openclaws XDG_RUNTIME_DIR=/run/user/1001 openclaw cron enable 875d1804-dd94-42b1-9fd1-136f20151b59
```

## Приёмка — отрицательная. ПРОЙДЕНА 21.09.2026

План требует: **сломать доставку и убедиться, что это видно снаружи.** Прогон:

1. доставка переведена на заведомо недоступный чат `999999999999`;
2. `openclaw cron run` — задача отработала;
3. результат прогона::

       completionStatus: failed
       deliveryStatus:   not-delivered
       delivered:        false
       deliveryError:    Telegram send failed: chat not found (chat_id=999999999999)

4. чат возвращён, повторный прогон: `completionStatus: succeeded`, `delivered: true`,
   отчёт доставлен в 5457896619.

🔴 **Главное, что вскрыла эта приёмка: отказ доставки виден в истории прогонов, но
НЕ виден в списке задач.** В `cron list` та же задача показывала `status: ok`. То есть
ежедневная сверка «все задачи ок» пропустила бы недоставку. Смотреть надо
`cron runs --id <id>` и поле `completionStatus`, а не статус в списке.

⚠️ Записи истории приходят **в порядке от старых к новым**: `entries[0]` — самый ранний
прогон. Читая `entries[0]`, легко принять давний отказ за свежий.

🔴 Шаг 3 обязателен именно в такой форме. Зелёный статус задачи не доказывает, что
сообщение дошло: в этом проекте уже был день, когда все одиннадцать мониторов показывали
«уведомление привязано», механизм срабатывал секунда в секунду, а отправка падала с
`chat not found`, потому что бот не был добавлен в группу.

## Что отчёт должен содержать

Текст собирается агентом из ответа `ozon_ad_report`, а не придумывается. Обязательные
величины — те же, что в самом отчёте: ДРР по управляемому расходу, отдельная строка
тарифа «оплата за заказ: все товары», доля рекламных заказов в общих, три аномалии и
**блок покрытия**.

⚠️ Покрытие выбрасывать из сообщения нельзя. Сумма расхода за неделю с несобранным днём
выглядит неделей с низким расходом, и по самому числу этого не видно.


## Выкатка, без которой задача не работала

Первый прогон упал не на доставке, а на отсутствии инструмента: ассистент ответил
*«инструмента `ozon_ad_report` у меня в наборе нет»* — и был прав. Весь код дня лежал в
форке, а контейнер на проде работал на прежнем образе.

Выкачено 21.09.2026: `/opt/ozon-mcp` обновлён, образ пересобран, контейнер пересоздан.
После пересборки шлюз увидел новые инструменты сам — `mcp probe` показал
`ozon_513b1590bcb44989__ozon_ad_report` и четыре других.

⚠️ Имена у шлюза **префиксуются сервером**: `<сервер>__<инструмент>`. Проверяя наличие
инструмента, сравнивать по вхождению, а не по равенству, — иначе получится ложное
«инструмента нет» на работающей связке. Я на этом споткнулся.

Хранилище ряда на проде создано в момент старта: `/opt/ozon-mcp/data/series.db`.
Первый сбор проведён вручную — 390 строк рекламы за 20.09, 887 карточек товаров,
325 строк остатков на 47 складах.

⚠️ Тем же прогоном сработал сторож незнакомых полей: Ozon прислал в `products/sku` поле
`dateAdded`, которого нет в замеренном контракте. Ряд от этого не пострадал — поле ушло
в `_unknown` и попало в итог сбора.
