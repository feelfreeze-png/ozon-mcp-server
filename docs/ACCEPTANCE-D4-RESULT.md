**НЕ ПРОВЕДЕНА.** Ядро по условию «б» дословно — **0 SKU** при пороге входа 50.

Это третий из трёх законных исходов, и в «ПРОЙДЕНА» он не сворачивается. Причина ниже

## Почему ядро пусто

Условие «б» требует `product_sku.source = 'fbo'`. Замерено:

| Величина | Число | Откуда |
|---|---|---|
| SKU в отчёте размещения за 21.09 | 97 | файл отчёта |
| из них с `source = 'fbo'` | **0** | `product_sku` на ноде |
| из них с `source = 'sds'` | **97** | там же |
| SKU отчёта за всё окно | 174 | файл |
| из них нашлись в `product_sku` | 174 | сверка |
| из них `sds` | **174 из 174** | сверка |
| SKU снимка 21.09 | 188, **все `sds`** | `stock_daily` |
| карточек с легаси-`fbo`-скю вообще | 123 из 887 | `product_sku` |
| SKU отчёта, у чьей карточки есть `fbo`-близнец | 12 | джойн по `product_id` |

Верхнеуровневый `sku` кабинета — это `sds`; `fbo`-скю существуют только как вторая,
легаси-строка у 123 карточек, и **их не печатает ни снимок, ни отчёт**. Значит условие
«б» не выполнится никогда, сколько ни ждать снимков: ядро останется нулевым.

Даже самое щедрое смягчение — «у карточки есть `fbo`-близнец» — даёт **12 SKU**, что
тоже ниже порога входа 50. Вывод устойчив к прочтению.

## Что показала сверка без условия «б» — ДИАГНОСТИКА, не приёмка

Печатается отдельно и в исход не засчитывается. Ядро «а + в + г» (есть строка отчёта за
21.09, есть снимок за 21.09 и 22.09, сумма по FBO-складам в обоих снимках одинакова):

| Величина | Число |
|---|---|
| ядро (а + в + г) | 87 SKU |
| двигались между снимками (вне ядра по «г») | 3 |
| **совпало с дельтой ровно 0** | **80 (92,0 %)** |
| не совпало | 7 |
| класс 1 — товар не FBO | 0 |
| класс 2 — тарификация считает иначе | запрещён на ядре по определению |
| класс 3 — ошибка сборки | 7 |
| не проверено (склад отчёта отсутствует в снимке) | 7 |
| SKU снимка вне отчёта с нулём по белому списку (класс 1 подтверждён) | 91 |
| SKU снимка вне отчёта с **не**нулём по белому списку | 0 |

Все семь несовпавших — **в одну сторону: отчёт больше снимка**, на 1–2 экземпляра.
Отрицательных дельт ноль. Это ровно то, чего ждал документ порога («отчёт ≥ снимок»,
неизвестное № 4), но классом 2 на ядре оно быть не может, поэтому засчитано классом 3.

В разрезе `sku × склад`: 106 пар отчёта за 21.09, из них 99 нашлись в снимке, **91
совпала значением**. Подбор счётчика снимка ничего не улучшил: `available_stock_count`
даёт 91 из 106, лучшая пара счётчиков (`available` + `valid`) — 95, то есть системной
подмены величины нет, остаток объясняется отсутствующими складами.

## 🔴 Что нашлось попутно: регистр имён складов

Обязательный побочный замер из документа — «сколько имён складов отчёта не
сопоставилось со снимком» — дал **5 из 44**. Разбор показал, что три из пяти — это
**разный регистр одного и того же склада**:

    отчёт:  Казань_РФЦ_НОВЫЙ        снимок:  КАЗАНЬ_РФЦ_НОВЫЙ
    отчёт:  Новосибирск_РФЦ_НОВЫЙ   снимок:  НОВОСИБИРСК_РФЦ_НОВЫЙ

Цена ошибки: на точном сравнении доля совпадений ядра была **74,5 %**, после свёртки
регистра — **92,0 %**. То есть отказ моста выглядел как расхождение данных. Сравнение
свёрнуто по регистру в `scripts/reconcile_d4.py`; свёртка делается в Python, потому что
`lower()` в SQLite кириллицу не сворачивает и дала бы тот же ложный результат.

Осталось два действительно отсутствующих склада: `Ростов_на_Дону_РФЦ` и
`Санкт_Петербург_РФЦ` — тарифицируются, но в снимке их нет ни под каким регистром
(в снимке есть другие: `РОСТОВ_НА_ДОНУ_2_РФЦ`, `СПБ_ШУШАРЫ_РФЦ`…). Их 7 SKU ушли в
