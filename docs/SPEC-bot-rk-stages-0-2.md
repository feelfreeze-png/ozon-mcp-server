> Ревизия 2, 2026-09-20. Основана на разведке шестью независимыми срезами и прошла
> враждебную проверку пятью линзами: 78 возражений, 56 опровергнуты скептиками, 22 приняты
> и учтены в этой ревизии.
>
> **Контракт документа:** каждое фактическое утверждение помечено одним из трёх способов
> проверки — **чтение кода** (механизм в коде есть, с Ozon не сверялся), **исполнение**
> (наш код запущен), **живой вызов** (ответ боевого кабинета). Непроверенное помечено
> ⚠️ **допущение**. Четвёртого состояния нет намеренно.

## 0. Зачем этот документ

Продукт — ассистент, управляющий рекламными кампаниями на Ozon. Карта развития (шесть
этапов) взята из проектной базы знаний и здесь не переизобретается. Спецификация описывает
**этапы 0–2 подробно**; этапы 3–6 — одним разделом «куда растём».

Документ отвечает на три вопроса: что система делает, чего намеренно не делает, и какие
отказы обязаны быть заметны.

## 1. Границы

**В границах:** каркас (этап 0), ежедневный отчёт без изменений (этап 1), управление
ставками и бюджетами с предохранителями (этап 2).

**Вне границ, намеренно** (список из базы знаний, дословно): заказы FBS и FBO вместе с
маркировкой; поставки FBO, склады и методы доставки; вопросы покупателей; списанные товары;
аналитика внешнего трафика; категории, бренды и сертификаты; любая запись в «Товарах».

Остатки берём из «Товаров» и «Аналитики», а не из группы «Склады» — это и есть «всё, что
связано со складами, кроме остатков».

## 3. Модель данных

### 3.1. Ключи товара

🔴 **`sku` не является уникальным ключом товара.** *Живой вызов:* у 124 из 856 карточек в
поле `sources` два разных `sku`. Типичная пара — **sds + fbo** (fbo встречается 118 раз,
fbs — 6); верхнеуровневый `sku` у 852 из 856 карточек это sds-скю.

**Канонический ключ товара — `product_id`.** `sku` — внешний идентификатор со
множественностью:

```
product_id ─┬─ offer_id (1:1)
            └─ sku (1:N, с пометкой источника: sds | fbo | fbs)
```

Таблица, построенная на `sku` как на первичном ключе, молча потеряет или задвоит товары.

### 3.2. Полнота ассортимента

*Живой вызов:* `/v3/product/list` с `visibility="ALL"` **не возвращает архивные карточки** —
856 против 31, пересечение нулевое. Полный ассортимент — объединение двух выборок.

### 3.3. Время

**Рекламные сутки Ozon — московские (UTC+3).** Подтверждено двумя независимыми способами:
тегом `Statistics` официальной спеки и границами `from=21:00:00Z` / `to=20:59:59Z` в самих
ответах API.

Требования:

1. **Хранить сутки в МСК.**
2. ⚠️ **Перевод Seller-дат из UTC применять только к меткам времени, не к агрегатам.**
   *Живой вызов:* измерение `day` в `/v1/analytics/data` **уже нарезано по Москве**.
   Механический перевод «всё, что из Seller, — UTC» сдвинет такой агрегат ещё на три часа.
   Каждое поле даты классифицируется явно: метка времени (переводим) или суточный агрегат
   (не трогаем).
3. **Каждое поле даты в ответе инструмента помечать поясом.** Неподписанная дата — дефект.
4. 🔴 **Запретить в коде поля `from`/`to` (RFC3339) у методов статистики.** *Живой вызов:*
   они выбирают дни по UTC, а имя файла в том же ответе рендерит их в МСК — два ответа на
   один запрос противоречат друг другу, оба выглядят правдоподобно. Только `dateFrom`/`dateTo`
   простыми датами.

## 4. Этап 0 — каркас

Пять требований. Первые два выполнены (§ 2), остальные три — нет.

### 4.1. Таблица `product_id ↔ offer_id ↔ sku`

Источник — `/v3/product/list` (обе выборки по § 3.2) и `/v3/product/info/list`.
*Живой вызов:* 856 карточек проходят одним запросом за 0,68 с; потолок не нащупан.

🔴 **Профили `catalog` и `orders` на проде выключены** (`OZON_TOOLSETS=ads,analytics`),
поэтому через MCP-поверхность таблица сейчас недостижима. Требование: включить `catalog` на
время этапа 1 при сохранении `OZON_READONLY=1`.

**Приёмка:** число строк равно сумме активных и архивных карточек; ни один `product_id` не
встречается дважды; для каждого `sku` из рекламной статистики находится ровно один
`product_id`.

### 4.2. Тип подписки кабинета

`POST /v1/seller/info`. ⚠️ **Не реализован**; инструменты группы «Компания» — заглушки,
отвечающие на несуществующий путь и возвращающие поле `error` с кодом 200 (§ 9).

От подписки зависит доступность поисковой аналитики и отзывов. ⚠️ **Замерено 21.09.2026:
уровни различаются между собой.** При `PREMIUM_PLUS` `/v1/analytics/product-queries` и
`/product-queries/details` работают, а `/v1/search-queries/top` отвечает 403 с текстом
«Method available with Premium Pro subscription». Писать «Premium Plus и Pro» как об одном
пороге нельзя — подробности в `docs/PLAN-search-analytics.md`.

### 4.3. Журнал действий

🔴 **Существующая таблица `tool_calls` — журнал ВЫЗОВОВ, а не действий.** По ней нельзя
ответить «какую ставку поставили, на каком SKU, какая была до».

Журнал действий хранит: объект, что изменено, прежнее значение, новое, инициатор, результат.
Нужен на этапе 2, **заводится на этапе 0** — прежние значения задним числом восстановить
неоткуда.

## 5. Этап 1 — ежедневный отчёт

**Продукт этапа:** «ДРР по SKU, доля рекламных заказов в общих, аномалии». Только
рекомендации, никаких изменений.

### 5.1. Источники

| Что | Метод | Свойства |
|---|---|---|
| Подневный срез по SKU | `POST /api/client/statistics/products/sku` | **Не расходует лимиты** (пометка в спеке). Только сегодня и вчера |
| Агрегат по кампании | `GET /api/client/statistics/campaign/product` | **Не расходует лимиты** (пометка в спеке). Период ≤62 дня ⁷ |
| Дневной срез по кампаниям | `GET /api/client/statistics/daily/json` | Пометки нет. Период ≤61 день ⁷ |
| Бэкфилл пропущенных дней | асинхронный отчёт | Расходует квоту. **Одновременная выгрузка ровно одна** ⁷ |

⁷ *Живой вызов.* Пометка «не расходует лимиты» стоит **ровно у двух** методов; отсутствие
пометки у остальных — ⚠️ **допущение**, а не доказательство обратного.

🔴 **Ни одного из двух основных методов в форке сейчас нет в пригодном виде.**

**Работа 1 — реализовать `POST /api/client/statistics/products/sku`.** В `client.py` его нет
ни в каком виде. Контракт выверен *живым вызовом:*

- тело `{date_from, date_to, campaignIds}` простыми датами;
- ⚠️ поле кампаний — **только `campaignIds` или `campaign_ids`**. Привычное по остальным
  методам `campaigns` даёт `400 {"error":"empty campaigns"}` — API утверждает, что кампаний
  не передали, хотя их передали, и это читается как «у аккаунта нет кампаний»;
- ответ: `sku, date, campaignId, expense, orders, modelOrders, sales, modelSales, drr, ctr,
  avgCpc, views, clicks, toCart, price`;
- разделитель дробной части здесь **точка**, в остальных методах запятая;
- 30 campaignIds проходят за 0,20 с; потолок не нащупан (в кабинете 248 SKU-кампаний).

**Работа 2 — исправить `ozon_ad_statistics_products`.** Инструмент описан как «CPC campaign
stats per product: spend, CTR, CPC, orders, ДРР», а вызывает `campaign/product/json`, который
отдаёт **одну строку на кампанию за весь период**: полей `sku` и `date` в ответе нет вовсе.
Отвечает успехом, цифры правдоподобные, уровень не тот — класс § 9.

**Решение:** основной съём — `products/sku` за «вчера» раз в сутки по МСК. *Живой вызов:* за
закрытый день 19.09 `products/sku`, `daily/json` и `campaign/product` сходятся до копейки
округления.

⚠️ **Допущение: цифры закрытого дня задним числом не меняются.** Не замерено (ревизия
атрибуции, отмены заказов). Цена ошибки несимметрична: `products/sku` отдаёт **только сегодня
и вчера**, значит переснять SKU-разрез позже можно лишь асинхронным отчётом, а он расходует
квоту. Требование: **сторож сверки** — раз в неделю переснимать один прошедший день
асинхронным отчётом и сравнивать с накопленным.

### 5.2. Семантика чисел

Каждое требование выведено из живого замера.

1. **`daily.orders = products/sku.orders + products/sku.modelOrders`**, и так же для сумм
   (8 = 6 + 2; 15 957,00 = 11 791,00 + 4 166,00). Сборщик складывает обе пары; ежедневная
   сверка «сумма по SKU = daily за тот же день» — сторож.
2. **`ctr` не читать ни из одного метода.** Три метода под одним именем дают три конвенции:
   доля, округлённая до двух знаков (при фактических 2,364% приходит `"0,02"`), процент, и
   число. Считать самим из `clicks`/`views`.
3. **Один парсер чисел на все методы:** `"2255,19"`, `"1256.36"`, и число без кавычек.
4. **Читать поля через значение по умолчанию.** Асинхронный отчёт **выбрасывает нулевые поля
   целиком**: строка по одному SKU не содержит ключей `clicks`, `orders` вовсе, соседняя их
   имеет.
5. ⚠️ **Дневной срез внутри текущего дня заморожен** минимум на 7 минут; верхняя граница не
   измерена. Продуктовое обещание «обновление каждые 30 минут» этими методами **не
   обеспечено** — расхождение фиксируем, а не замалчиваем.

### 5.3. Знаменатель: общие заказы по SKU

Метрика «доля рекламных заказов в общих» требует знаменателя, которого нет ни в одном
рекламном методе. Источник — `/v1/analytics/data` (измерение `sku` × `day`, метрика заказов).

⚠️ *Живой вызов:* этот эндпоинт **молча выбрасывает неизвестные метрики и измерения** вместо
ошибки. Требование: белый список допустимых значений, снятый опытным путём, и сторож
«запрошено N измерений — получено N».

### 5.4. Ряд остатков

🔴 **Ни одна из семи синхронных остаточных ручек Seller API не отдаёт историю «sku × день».**
*Живой вызов* по `/v4/product/info/stocks`, `/v2/analytics/stock_on_warehouses`,
`/v1/analytics/stocks`, `/v1/analytics/turnover/stocks` и трём складским — измерения даты нет
ни у одной.

✅ **История FBO-остатков доступна задним числом.** Прогон отчётных путей выполнен
2026-09-20 с разрешения владельца, результат:

- 🔴 `POST /v1/report/products/movement/create` и `POST /v1/report/stock/create` **не
  существуют**: оба отдают `404 page not found`, хотя роль ключа их разрешает. *Живой
  вызов.* Список из `/v1/roles` перечисляет несуществующие пути — доверять ему как каталогу
  возможностей нельзя.
- ✅ **`POST /v1/report/placement/by-products/create` отдаёт подневный ряд.** *Живой вызов:*
  строка на **дату × SKU × склад**, колонки `Дата | SKU | Артикул | Категория | Склад | …
  Кол-во экземпляров | Платный объём | Начисленная стоимость размещения`. Формат XLSX, не
  CSV. Ограничения: **период ≤31 день**, **не более 5 отчётов в сутки**.
- **Глубина хранения — не меньше 6,5 месяцев:** отчёт за 2026-03-01…03-31 отдан полностью.
  Нижняя граница не нащупана.

Следствия:

1. **Тезис «каждый несобранный день потерян навсегда» неверен для FBO.** Бэкфилл возможен:
   31 день за прогон × 5 прогонов в сутки = до 155 дней истории в день.
2. ⚠️ **Только FBO.** Остатки FBS и rFBS этот отчёт не покрывает; для них допущение о
   невосстановимости остаётся в силе.
3. ⚠️ **Допущение: `Кол-во экземпляров` равно остатку.** Это величина для тарификации
   хранения. Сверка с остаточными ручками за один известный день не делалась.

**Решение не меняется: ряд накапливаем сами, ежедневным снимком.** Бэкфилл — страховка от
сбоя, а не замена сбору: он ограничен пятью прогонами в сутки, покрывает только FBO и даёт
величину тарификации, а не остаток.

Источник снимка и его измеренные ограничения:

| Ручка | Ограничение (живой вызов) |
|---|---|
| `/v1/analytics/turnover/stocks` | **1 запрос в минуту**; именно её зовёт `ozon_stock_on_warehouses` вопреки своему имени |
| `/v1/analytics/stocks` | перемежает 429 и HTTP 500 даже при остатке лимита ~30: на 20 запросах с паузой 1,5 с — 11 успехов, 9 отказов; **≤100 SKU** за раз |
| `/v4/product/info/stocks` | 🔴 клиент шлёт `last_id`, а курсор в ответе называется `cursor` — **пагинация молча не работает** |

Требование: выбрать ручку явно, реализовать её ограничения (чанкинг, паузы, ретраи,
правильное имя курсора) и завести **сторож непрерывности ряда** — пропущенный день обязан
быть виден.

### 5.5. Пагинация и чанкинг

🔴 `ozon_ad_campaigns` **не имеет пагинации**: зашиты `page=1, page_size=100` при 248
SKU-кампаниях. Кабинет виден меньше чем наполовину, ни один признак на это не указывает.

Требования: пробросить `page`/`page_size`, вернуть `total` наружу, чанкинг под лимиты.

⚠️ **Числа лимитов — из справочника базы знаний, не замерены:** ≤200 SKU в конкурентных
ставках, ≤500 товаров в кампанию, ≤10 кампаний на асинхронный отчёт, ставки 500/час и
6000/день, бюджеты 100/час и 500/день. Тот же справочник уже один раз разошёлся с замером
(§ 6.2), поэтому каждое число проверяется перед тем, как на него опереться. *Замерено живьём
только одно:* 30 campaignIds на `products/sku` проходят.

### 5.6. Что считается рекламным расходом

**В ДРР входит весь управляемый рекламный расход — CPC и CPO по выбранным товарам.**

Из ДРР исключается ровно одна сущность: режим **«Оплата за заказ: все товары»**
(`all_sku_promo`). Это тариф 5%, ставка в нём одна на кабинет, по SKU не управляется и
рычагом агента не является. Показывается **отдельной строкой** отчёта.

Обоснование из базы знаний: сложив тариф с управляемой рекламой, агент получит завышенный ДРР
и начнёт резать работающие кампании. Обратная ошибка так же дорога: выбросив из ДРР
управляемый CPO, агент на этапе 2 двигает ставку, эффект которой не измеряет.

Правило закрепляется **в сборщике, а не в промпте модели**.

## 6. Этап 2 — управление

### 6.1. Предохранители

Ни один из пяти не реализован. Сейчас их отсутствие закрыто **только** флагом
`OZON_READONLY=1`; в момент снятия флага защиты не будет никакой.

1. Потолок изменения ставки за итерацию (±15–20%) и абсолютный потолок ставки
2. Белый список кампаний, которые агенту можно трогать
3. Сохранение прежней ставки для отката
4. Счётчик лимитов: **часового и суточного окна одновременно**
5. Схема «прочитать → изменить → отправить целиком» для `PUT /campaign/{id}/products`

🔴 **Пятый не формальность:** `PUT` перезаписывает список целиком и вместе с ним стирает
стоп-слова и фразы со ставками. Запрос возвращает успех.

🔴 **Часовые лимиты упираются раньше суточных** — автоматика, рассчитанная на суточный лимит,
встанет через час.

### 6.2. Единицы измерения — блокер этапа 2

⚠️ **Не определено.** Справочник базы знаний утверждает «бюджеты в копейках», код форка
конвертирует рубли в микрорубли. Расхождение в 10 000 раз.

🔴 **Очевидный способ разрешения не работает:** *живой вызов* — поле `budget` равно нулю у
100 кампаний из 100, сверять не с чем.

Требование к замеру: разрешать **чтением** через `GET /api/client/limits/list` (поля
`minBid`/`maxBid`) против минимальных ставок в интерфейсе кабинета, и отдельно для ставки —
через `ozon_ad_min_bids`, который уже отдаёт числа (7, 7, 8 — *живой вызов*). Замер обязан
покрыть **и ставки, и бюджеты**: расхождение заявлено про обе величины, а предохранитель № 1
(абсолютный потолок ставки) без единиц не формулируется.

## 7. Хранение и чтение

**Писатель — сам контейнер `ozon-mcp`:** у него ключи Ozon; у хостового скрипта их нет, и
заводить второе место для секрета нельзя.

**Читатель — он же, новым MCP-инструментом.** Иначе накопленное некому прочитать: у ассистента
нет доступа к нашему хранилищу, у платформенного backend нет ключей и сетевого пути. Отчёт
этапа 1 собирается инструментом, а не внешним запросом к базе.

**Хранилище — отдельное, рядом со `stats.db`, не внутри.** `stats.db` — телеметрия с
ротацией; смешав, получим ретенцию одной таблицы, удаляющую другую.

🔴 **`/opt/ozon-mcp` не попадает в бэкап, и это не поднимает ни одного сигнала.** Все четыре
признака здоровья бэкапа остаются зелёными.

Срочность снижена находкой § 5.4: ряд FBO-остатков восстановим из Ozon бэкфиллом (≤155 дней
за сутки). **Но блокером быть не перестал:** рекламная статистика по SKU этим путём не
восстанавливается вовсе (`products/sku` отдаёт только сегодня и вчера), остатки FBS не
покрыты, и `Кол-во экземпляров` — величина тарификации, а не остаток. Покрытие бэкапом
делается в первом же пакете работ, но перестало блокировать старт сбора.

🔴 **Bind-mount держится только на override-файле**, рядом живёт осиротевший том. `docker
compose up` без override молча переключит сервер на пустой том: магазинов нет, ключей нет,
сервер работает.

⚠️ **В sqlite форка нет механизма миграций:** `ALTER TABLE` обёрнут в `try/except` с пустой
веткой — любой отказ, включая «база заблокирована», проглатывается.

## 8. Гейты между этапами

| Переход | Условие |
|---|---|
| 0 → 1 | Каркас собран, таблица товаров сходится, сбор идёт без пропусков |
| **1 → 2** | **Цифры агента сходятся с кабинетом** по расходу, заказам и ДРР. Обычно 1–2 недели |
| 2 → 3 | Автоставки работают без откатов |

🔴 **Сходимость трёх методов API между собой не засчитывается за сверку с кабинетом.** Она
доказана живьём до копейки — и это сходимость API с самим собой. В базе знаний зафиксирован
противоположный случай: выгрузка кампаний дала 35 718 ₽ против фактических 212 076 ₽ — почти
вшестеро меньше, без единой ошибки и выглядя правдоподобно.

Сверка 1→2 — **письменная, человеком, с фиксацией дельты** по трём величинам.

## 9. Отказы, которые обязаны быть заметны

Самый дорогой класс дефекта в этом проекте — отказ, неотличимый от нормы. Каждый пункт
проверен живьём.

| Отказ | Как выглядит сейчас | Что требуется |
|---|---|---|
| Предохранитель размера режет ответ | Предупреждение уходит **отдельным текстовым блоком**, не в JSON | Признак усечения **внутри** JSON (`truncated`, `total`, `shown`); сборщик обязан его требовать |
| Режим `compact` выбрасывает поля | Молча, без следа в JSON | Белые списки полей — по живым ответам |
| Инструмент вернул отказ | Плоский текст `Ошибка: …` | Структурный отказ. Сборщик различает **четыре** исхода: данные / пусто-подтверждённое / пусто-неизвестное / отказ ⁸ |
| Три инструмента отвечают полем `error` с кодом 200 | Выглядит как данные | Снять из каталога либо бросать исключение |
| Пагинация `last_id` не работает | Молча отдаёт первую страницу | Правильное имя курсора + сверка с `total` |
| Пропущен день сбора | Никак | Сторож непрерывности ряда |
| cron-задача выключилась сама | После 10 падений подряд; `cron list` без `--all` её **не показывает** | Сверка только с `--all` |
| Отчёт не доставлен | `--best-effort-deliver` **гасит именно этот сигнал** | Не ставить его на отчётную задачу |

⁸ «Пусто» у Ozon означает минимум три разных вещи: активности не было; запрос не попал в
окно; фильтр отсёк всё. Схлопнув их в один исход, мы воспроизводим ровно то, от чего раздел
защищает.

## 10. Куда растём (этапы 3–6)

**3. Экономика** — предельный ДРР из юнит-экономики, переход с ДРР по заказам на ДРР по
