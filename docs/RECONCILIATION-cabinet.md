## Зачем это отдельная работа

Три метода Ozon API уже сошлись между собой до копейки. Это сходимость API с самим
собой, и за сверку она не засчитывается: в базе знаний записан случай, когда выгрузка
дала 35 718 ₽ против фактических 212 076 ₽ — без единой ошибки, без единого отказа, все
внутренние проверки зелёные.

Поэтому вторую колонку обязан заполнить **человек, глядя в кабинет**. Ни я, ни агент
этого сделать не можем: у нас нет доступа к интерфейсу, только к API — то есть ровно к
тому источнику, который и проверяется.

## 🔴 Порядок, без которого сверка бессмысленна

1. Числа агента записаны **первыми** и закоммичены в git. Отметка времени коммита — и
   есть доказательство, что их не подгоняли под увиденное.
2. Владелец открывает кабинет и вписывает свои числа, **не меняя** первой колонки.
3. Дельты считаются механически, пороги — ниже, и они записаны **до** чтения кабинета.

Если делать наоборот, критерий «расхождение объяснено» провалиться не может: объяснимо
любое расхождение, а судьёй выступает тот, кто писал сборщик.

## Пороги, записанные заранее

| Величина | Допуск | Почему такой |
|---|---|---|
| Расход, всего за день | **≤ 0,5 %** | оба числа из одного источника, разойтись может только округление экрана |
| Расход отдельной кампании | **≤ 1 %** | итог может сойтись при взаимно гасящихся ошибках — поэтому сверяются и слагаемые |
| Заказы | **точное совпадение** | целые числа, допуска быть не может |
| Выручка | **≤ 1 %** | окно атрибуции может сдвинуть сумму |
| ДРР | **≤ 0,5 п.п.** | производная от двух предыдущих |
| Показы, клики | **≤ 0,5 %** | |

Любая величина вне допуска → сверка **ПРОВАЛЕНА** за этот день. Не «объяснена», а
провалена; разбор идёт после, и его вывод не отменяет результат.

## ⚠️ Что НЕ обязано сойтись — названо заранее

Перечислено здесь, чтобы потом это нельзя было использовать как оправдание задним числом.

1. **«Выручка» у нас — рекламная, а не выручка магазина.** Это `sales` из рекламной
   статистики, то есть приписанная рекламе. Общий оборот магазина за день будет больше,
   и сравнивать надо не с ним.
2. **Наш ДРР исключает режим «Оплата за заказ — все товары».** За 20.09 расход по нему
   ноль, поэтому в этот день исключение ни на что не влияет и числа сопоставимы. В день
   с ненулевым тарифом их пришлось бы сравнивать иначе.
3. **Заказы у нас — сумма `orders` и `model_orders`** (32 + 1 = 33). Если кабинет
   показывает их двумя строками, складывать; если одной — сверять с суммой.
4. **Время.** Наш день — московские сутки целиком, 00:00–23:59 МСК. Если в кабинете
   выбран другой пояс или период «за 7 дней», числа не сопоставимы вообще.
5. **Числа могут измениться задним числом.** Окно атрибуции у Ozon сдвигает заказы и
   выручку спустя дни. Поэтому в таблице есть **дата снятия** для каждой стороны: если
   они разойдутся на несколько дней, расхождение может быть настоящим и при исправном
   сборщике.

## Что нужно сделать владельцу

Пять шагов, один день, минут десять.

1. Кабинет Ozon → раздел **Продвижение → Статистика** (или «Отчёты по кампаниям»).
2. Период — **ровно 20.09.2026, один день**. Не «неделя», не «последние 7 дней».
3. Выписать в таблицу выше: расход, заказы, выручку, ДРР, показы, клики, число кампаний
   с ненулевым расходом.
4. Провалиться в пять кампаний из второй таблицы по их номерам и выписать расход
   по каждой.
5. Записать, **с какого именно экрана** сняты числа, и дату снятия. Без этого повторить
   сверку через месяц будет невозможно: у Ozon несколько экранов с разными числами, и
   какой из них мы сверяли, через месяц никто не вспомнит.

Если какой-то величины на экране нет — так и написать «нет на экране». Пустая клетка и
«нет такой величины» — разные вещи, и вторая тоже результат.

## Вердикт

Допустимы ровно три:

* **ПРОЙДЕНА** — все величины дня в допуске, обе даты снятия записаны.
* **ПРОВАЛЕНА** — хотя бы одна вне допуска. Указать какая и на сколько.
* **НЕ ПРОВЕДЕНА** — колонка кабинета пуста или период не совпал.

Сейчас: **НЕ ПРОВЕДЕНА** — заполнена одна сторона из двух.
