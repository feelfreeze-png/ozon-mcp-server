## Общие правила итерации

1. **`OZON_READONLY=1` не снимается ни на минуту.** Любая правка, приближающая запись в
   Ozon, в эту итерацию не входит.
2. **Один пакет — один PR.** Ворота форка зелёные перед каждым: `pytest`, а для скриптов
   платформы ещё и `shellcheck -S warning`.
3. **Отрицательный тест обязателен там, где положительный ничего не значит.** Если приёмка
   может пройти на сломанной системе, она не приёмка.
4. **Живой кабинет — только чтение.** Не больше 3–4 запросов подряд к одному эндпоинту,
   паузы между ними. Отчёты о размещении — не больше 5 в сутки на весь кабинет, и они общие
   с бэкфиллом D4.

# Пакет A — фундамент

## A1. Покрыть `/opt/ozon-mcp` бэкапом

**Репозиторий:** платформа `55in1-openclaws` (не форк).
**Файлы:** `src/infra/scripts/backup.sh`, `src/infra/prod-manifest.tsv`.

**Работа.** Добавить `/opt/ozon-mcp` в состав архивируемого. Каталог root-only, внутри
`.env` с токенами и `data/` с шифрованным стором магазинов.

⚠️ **Секреты попадут в бэкап.** Так же устроен `~/.openclaw`, который архивируется целиком —
то есть это не новый класс, но записать в рансбук обязательно.

**Приёмка — восстановлением, а не кодом возврата:**

```bash
ssh lilu 'set -a; . /root/.restic-env; set +a; restic snapshots --tag openclaws-db --latest 1'
ssh lilu 'restic restore <snapshot> --target /tmp/restore-probe --include /opt/ozon-mcp'
ssh lilu 'ls -la /tmp/restore-probe/opt/ozon-mcp/data/'
```

Зелёным считается: `shops.json` и `.encryption_key` присутствуют, файл среза читается.
Код возврата юнита доказательством **не является** — он расходится с фактом в обе стороны.

## A2. Закрепить bind-mount

**Репозиторий:** форк. **Файлы:** `docker-compose.yml`, удалить
`docker-compose.override.yml` на ноде.

**Работа.** Перенести `./data:/data` в основной compose. Удалить осиротевший том
`ozon-mcp_ozon_data`.

**Приёмка:**

```bash
ssh lilu 'cd /opt/ozon-mcp && mv docker-compose.override.yml /tmp/ && docker compose up -d && sleep 8'
ssh lilu 'curl -sS -H "Authorization: Bearer $(sed -n "s/^ADMIN_TOKEN=//p" /opt/ozon-mcp/.env)" http://127.0.0.1:8004/api/key-expiry'
ssh lilu 'docker volume ls | grep ozon'
```

Зелёным считается: магазин `main` виден **без** override-файла; осиротевшего тома нет.

## A3. Хранилище среза

**Репозиторий:** форк. **Новый файл:** `ozon_mcp/series.py`.

**Почему отдельная база.** `stats.db` — телеметрия с ротацией (`health_checks` чистится
`DELETE … LIMIT 1000`), деловые ряды в ней смешивать нельзя. Файл: `/data/series.db`.

**Схема:**

```sql
-- версия схемы; отказ миграции ОБЯЗАН быть виден, а не проглочен
CREATE TABLE schema_version (version INTEGER NOT NULL);

-- рекламный срез: дата в МСК
CREATE TABLE ad_daily (
  date_msk    TEXT NOT NULL,       -- YYYY-MM-DD, московские сутки
  sku         INTEGER NOT NULL,
  campaign_id INTEGER NOT NULL,
  shop_id     TEXT NOT NULL,
  expense     REAL, views INTEGER, clicks INTEGER, to_cart INTEGER,
  orders      INTEGER, model_orders INTEGER,
  sales       REAL,    model_sales  REAL,
  price       REAL,
  source      TEXT NOT NULL,       -- products_sku | backfill_report
  fetched_at  TEXT NOT NULL,       -- ISO-8601 с поясом
  PRIMARY KEY (date_msk, sku, campaign_id, shop_id)
);

-- остатки: дата в МСК, разрез по складу
CREATE TABLE stock_daily (
  date_msk   TEXT NOT NULL,
  sku        INTEGER NOT NULL,
  warehouse  TEXT NOT NULL,
  shop_id    TEXT NOT NULL,
  qty        INTEGER,
  source     TEXT NOT NULL,        -- snapshot | placement_report
  fetched_at TEXT NOT NULL,
  PRIMARY KEY (date_msk, sku, warehouse, shop_id)
);

-- товары: product_id канонический, sku множественный
CREATE TABLE product (
  product_id INTEGER NOT NULL, shop_id TEXT NOT NULL,
  offer_id   TEXT, name TEXT, archived INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (product_id, shop_id)
);
CREATE TABLE product_sku (
  product_id INTEGER NOT NULL, shop_id TEXT NOT NULL,
  sku        INTEGER NOT NULL, source TEXT,   -- sds | fbo | fbs
  PRIMARY KEY (sku, shop_id)
);

-- журнал ДЕЙСТВИЙ (не вызовов) — заводится сейчас, используется на этапе 2
CREATE TABLE action_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  at TEXT NOT NULL, shop_id TEXT NOT NULL,
  object_kind TEXT NOT NULL, object_id TEXT NOT NULL,
  field TEXT NOT NULL, value_before TEXT, value_after TEXT,
  actor TEXT NOT NULL, result TEXT NOT NULL, error TEXT
);
```

🔴 **`source` в двух рядах обязателен.** Снимок и бэкфилл смешивать нельзя: бэкфилл покрывает
только FBO и даёт величину тарификации, а не остаток.

**Приёмка.**

```bash
uv run pytest tests/test_series_schema.py -q
```

Тесты обязаны включать: миграция с нуля; повторный прогон идемпотентен; **отрицательный** —
при сломанной миграции вызов падает, а не проглатывает ошибку (нынешний `try/except` с пустой
веткой этого не делает).

# Пакет B — честность ответов

## B1. Признак усечения внутрь JSON

**Файл:** `ozon_mcp/shaping.py`.

**Сейчас:** потолок 60 000 символов режет записи, а предупреждение уходит **отдельным
текстовым блоком** `TextContent`. Сборщик, читающий JSON, усечения не видит.

**Требуется:** поля внутри JSON — `_truncated: true`, `_total: N`, `_shown: M`.
Текстовый блок для человека сохранить.

**Приёмка.** Тест на ответе, превышающем потолок: признак присутствует, `_shown` равно числу
строк в JSON, `_total` — числу до обрезки. Плюс тест, что при отсутствии обрезки признака нет.

⚠️ **Когда делать:** перед E2, не перед C. Сборщик шейпинга не видит — он зовёт клиент
напрямую, минуя `call_tool` (`server.py:110-124`, контекст выставляет только `call_tool`).

## B2. Структурный отказ и четыре исхода

**Файл:** `ozon_mcp/server.py:985-988`.

**Сейчас:** `return [TextContent(text=f"Ошибка: {type(e).__name__}: {e}")]` — плоский текст.

**Требуется:**

```json
{"_error": {"kind": "ozon_http|ozon_business|our_bug|network",
            "status": 429, "message": "…", "retryable": true}}
```

Сборщик различает четыре исхода: **данные** / **пусто-подтверждённое** (Ozon ответил 200 и
пустым списком) / **пусто-неизвестное** (обрезка, отказ разбора) / **отказ**.

**Приёмка.** Тест на каждый исход. Отдельно: тест, что «пусто-подтверждённое» и
«пусто-неизвестное» **не сливаются**.

## B3. Часовые пояса

**Файлы:** `ozon_mcp/client.py`, `ozon_mcp/diagnostics.py:64`, `ozon_mcp/stats.py:217`.

Три работы:

1. **Классификация полей даты.** Реестр: имя поля → метка времени (переводим из UTC в МСК)
   или суточный агрегат (не трогаем). ⚠️ `day` из `/v1/analytics/data` **уже московский** —
   механический перевод сдвинет его ещё на три часа.
2. **Запрет `from`/`to`** у методов статистики в коде: они выбирают дни по UTC, а имя файла в
   том же ответе рендерит их в МСК.
3. **Починить две известные точки:** `diagnostics.py:64` формирует дату по локальному времени
   хоста и подписывает её `Z`; `stats.py:217` считает «сегодня» по UTC.

**Приёмка — три проверки, инвариантности мало.**

🔴 Одно сравнение двух `TZ` проходит на равномерно неверном коде: если всё считается по UTC,
оба прогона совпадут.

1. **Оракул:** `2026-09-19T21:30:00Z` → московские сутки `2026-09-20`. Жёсткая пара.
2. **Не-перевод агрегата:** `day` из `/v1/analytics/data` остаётся тем же днём.
3. **Инвариантность:**

```bash
TZ=Asia/Tashkent uv run pytest tests/test_timezones.py -q
TZ=UTC           uv run pytest tests/test_timezones.py -q
```

Плюс тест, запрещающий `from`/`to` у методов статистики.

## B4. Инструменты, которые лгут

**Файлы:** `ozon_mcp/server.py` (описания), `ozon_mcp/client.py:1441-1442`.

1. `ozon_ad_balance`, `company_info`, `company_tariffs` отвечают полем `error` с кодом 200 —
   снять из каталога либо заставить бросать исключение.
2. `ozon_ad_statistics_products` описан как «ДРР по SKU», а отдаёт агрегат по кампании: полей
   `sku` и `date` в ответе нет. Описание привести к факту.

**Приёмка.** Сторож-тест: для каждого инструмента, обещающего в описании поле, ответ это поле
содержит. Прогон на живых ответах, снятых с ноды, а не на выдумке.

# Пакет C — сбор рекламы

## C1. `products/sku`

**Файлы:** `ozon_mcp/client.py` (метод), `ozon_mcp/server.py` (инструмент, профиль `ads`).

**Контракт — выверен живым вызовом:**

```
POST /api/client/statistics/products/sku
тело: {"date_from": "YYYY-MM-DD", "date_to": "YYYY-MM-DD", "campaignIds": [...]}
```

🔴 **Поле кампаний — только `campaignIds` или `campaign_ids`.** Привычное по остальным методам
клиента `campaigns` даёт `400 {"error":"empty campaigns"}` — API утверждает, что кампаний не
передали, хотя их передали, и это читается как «у аккаунта нет кампаний».

Ответ по строке: `sku, date, campaignId, expense, orders, modelOrders, sales, modelSales,
drr, ctr, avgCpc, views, clicks, toCart, price`.

⚠️ **Разделитель дробной части здесь точка** (`"1256.36"`), в остальных методах запятая
(`"2255,19"`). Парсер чисел — **один на все методы**, принимает обе формы.
⚠️ **Окно — только сегодня и вчера.** Вне окна: `400 date range must contain only today or
yesterday`.
⚠️ **`ctr` не читать** — три метода под этим именем дают три разные конвенции. Считать самим
из `clicks`/`views`.

Замерено: 30 `campaignIds` проходят за 0,20 с; потолок не нащупан (в кабинете 248 SKU-кампаний).

**Приёмка.** Живой вызов; сумма `expense` по SKU равна `daily/json` за тот же закрытый день
(проверено: расхождение 1 копейка от округления). Плюс сверка семантики:
`daily.orders = Σ(orders) + Σ(modelOrders)`.

## C2. Ретраи и очередь выгрузок

**Файл:** `ozon_mcp/client.py`, класс `OzonPerformanceClient`.

**Сейчас:** у `OzonSellerClient` ретраи есть (`_RETRY_STATUSES={429,500,502,503,504}`,
`Retry-After`, экспонента до 10 с), у Performance — **нет**.

**Требуется:** тот же механизм. Плюс очередь на асинхронные выгрузки: **ровно одна активная
на аккаунт** — второй `POST /api/client/statistics` отдаёт
`429 {"error":"Превышен лимит активных запросов (максимум 1)"}` мгновенно.

⚠️ API **не отдаёт** ни `Retry-After`, ни `X-RateLimit-*` — паузу выбираем сами, с запасом.

**Приёмка.** Тест на 429 с повтором; тест, что вторая выгрузка ждёт первую.

## C3. Пагинация кампаний

**Файлы:** `ozon_mcp/server.py` (схема `ozon_ad_campaigns`), диспетчер.

**Сейчас:** зашиты `page=1, page_size=100` при 248 SKU-кампаниях и 1700 всего. Клиент
пагинацию уже умеет (`client.py:1253-1270`) — не проброшена наружу.

**Требуется:** проброс `page`/`page_size`, возврат `total` из ответа Ozon.

⚠️ Список кампаний **режется лимитом жёстче документированного**: второй запрос подряд даёт
`429`. Полный обход — с паузами (замерено: 9 с между страницами проходит).

**Приёмка — оракул из ответа.** Обход собрал ровно `total` записей; страниц
`ceil(total/page_size)`. 🔴 **Отрицательный тест:** оборванная пагинация ловится сверкой с
`total`, а не проходит молча. Абсолютных чисел в приёмке нет — они устареют.

## C4. Ежедневный сбор

**Новый файл:** `ozon_mcp/collector.py`. Запуск — из `_health_loop`-подобного цикла в
`app.py` либо отдельной задачей.

**Работа.** Раз в сутки по МСК, с запасом после полуночи: обойти SKU-кампании, снять
`products/sku` за «вчера», записать в `ad_daily` с `source='products_sku'`.

🔴 **Путь вызова:** методы клиента **напрямую**, мимо `call_tool`. От этого зависит порядок
пакетов: шейпинг и текстовые ошибки сборщика не касаются.

**Приёмка.** Два прогона подряд не задваивают строки (первичный ключ
`date_msk, sku, campaign_id, shop_id`). Прогон за уже собранный день перезаписывает, а не
дублирует.

## C5. Два сторожа

**Сторож непрерывности.** Дыра в `ad_daily` по дням — алерт. Отличать «данных нет, потому что
не собирали» от «данных нет, потому что расхода не было»: второе — строки с нулями, первое —
отсутствие строк.

**Сторож сверки.** Раз в неделю переснять один прошедший день асинхронным отчётом и сравнить
с накопленным. ⚠️ Это проверка допущения «цифры закрытого дня задним числом не меняются» —
оно **не замерено**.

**Третий сторож — сумма по SKU против `daily`.** Спека называет его ежедневным, а не разовой
приёмкой C1: разовая доказывает, что код верен сегодня, ежедневная — что Ozon не сменил
семантику.

**Приёмка — отрицательная, для каждого по отдельности:** удалить день (непрерывность);
подменить значение (сверка); сломать семантику (сумма). Отдельно: день из нулей сторож
непрерывности трогать не должен — расхода не было ≠ не собирали.

# Пакеты D–F

Расписываются перед стартом ветки. Здесь — только то, что уже определено и не изменится.

**D1.** 🔴 **Сначала расширить `readonly.WRITE_TOOLS` на пишущие всех профилей, и только
потом включать `catalog`.** Замер: в `catalog` 28 инструментов, 10 пишущих, `OZON_READONLY`
не блокирует **ни одного** — включая `ozon_product_delete`, `ozon_product_archive` и
`ozon_product_update_images` (стирает всё, что не передано). Приёмка поимённо по десяти, а не
счётом.
**D2.** Таблица товаров: `/v3/product/list` дважды (`visibility="ALL"` **и** `ARCHIVED` —
пересечение нулевое, 856 и 31) плюс `/v3/product/info/list`. Ключ — `product_id`; `sku`
множественный, с пометкой источника.
**D3.** Снимок остатков. Ограничения замерены: `/v1/analytics/turnover/stocks` — **1 запрос в
минуту**; `/v1/analytics/stocks` — перемежает 429 и HTTP 500, ≤100 SKU за раз;
`/v4/product/info/stocks` — 🔴 клиент шлёт `last_id`, а курсор в ответе называется `cursor`,
пагинация молча не работает.
**D4.** Бэкфилл FBO из `/v1/report/placement/by-products/create`: XLSX, период ≤31 день,
**5 прогонов в сутки**, глубина не меньше 6,5 месяцев. Колонки: `Дата | SKU | Артикул |
Категория | Склад | … | Кол-во экземпляров`. Писать с `source='placement_report'`.

**E1.** Знаменатель из `/v1/analytics/data`. ⚠️ Эндпоинт **молча выбрасывает неизвестные
метрики и измерения** — нужен белый список и сторож «запрошено N — получено N». Приёмка — на
**частично** неверном наборе: тест со всеми неверными метриками зеленеет без нашего сторожа,
ошибку выдаст сам Ozon.
**E2.** MCP-инструмент чтения ряда.
**E3.** Сборка отчёта. ДРР по управляемому расходу (CPC **и** CPO); исключается ровно
`all_sku_promo` — тариф 5%, отдельной строкой. Правило в сборщике, не в промпте.
**E4.** Доставка. ⚠️ **Без `--best-effort-deliver`** — он гасит сигнал о недоставке. Сверка
задач только с `--all`: задача выключается сама после 10 падений подряд и из списка исчезает.

**C6.** Чанкинг под лимиты (≤100 SKU в аналитике остатков, ≤200 в конкурентных ставках, ≤500
товаров в кампанию, ≤10 кампаний на отчёт) и пометка у каждого числа: замерено или взято из
справочника. Приёмка: граница проходит, граница+1 отвергается **нами**, а не Ozon.

**F1.** `POST /v1/seller/info` — тип подписки.
**F2.** Запись в `action_log` (схема уже в A3).

## Чего в этой итерации нет

Записи в Ozon в любом виде. Предохранителей этапа 2. Целевого ДРР и юнит-экономики — решение
владельца, вход этапа 3. Поисковой аналитики — требует Premium, тип подписки выясняется в F1.
Отзывов, цен, акций.
