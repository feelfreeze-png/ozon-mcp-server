# Подключение продавца Ozon

Порядок действий от «есть аккаунт на Ozon» до «ассистент отвечает по его кампаниям».
Рассчитан на повторение: один проход на каждого нового продавца.

Всё, что здесь написано, проверено на живом аккаунте 2026-09-18. Места, которые
проверены не были, помечены явно — их нельзя читать как «работает».

---

## 0. Что понадобится

Ozon выдаёт **две разные пары ключей**, в разных разделах кабинета, с разными
правилами. Одна другую не заменяет.

| | Performance API | Seller API |
|---|---|---|
| Что даёт | кампании, ставки, статистика рекламы | остатки, аналитика, товары |
| Раздел кабинета | Настройки → API-ключи | Настройки → Seller API |
| Что получаете | `client_id` + `client_secret` | `Client-Id` + `Api-Key` |
| Форма `client_id` | `<id>@advertising.performance.ozon.ru` | **положительное число** |
| Срок жизни | до отзыва | **3 месяца** |
| Механизм | OAuth2 client_credentials, токен на 30 мин | статические заголовки |

> ⚠️ **Самая частая ошибка — вписать одну пару в обе секции.** Внешне они похожи, и
> сервер примет обе. Отвалится потом: реклама будет работать, а остатки молча
> отвечать `400 Client-Id header value should be positive integer`. Проверка в § 5
> ловит это за минуту.

---

## 1. Ключи Performance API (реклама)

1. Личный кабинет → **Настройки → API-ключи**, выбрать **Performance API**
2. Если аккаунта Ozon Performance нет — создать; если есть — выбрать его
3. **Добавить новый ключ**
4. Сохранить `client_id` и `client_secret`

`client_id` имеет вид `XYZ@advertising.performance.ozon.ru`. Если в кабинете он
показан без суффикса — ничего дописывать руками не надо, сервер допишет сам
(`ozon_mcp/client.py`, `PERF_CLIENT_ID_SUFFIX`). Но знать об этом стоит: **при
ручной проверке curl'ом короткая форма даёт `401 invalid_client`**, и текст ошибки
причину не называет.

Проверить пару, ничего не поднимая:

```bash
curl -sS -X POST https://api-performance.ozon.ru/api/client/token \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"<ID>@advertising.performance.ozon.ru","client_secret":"<SECRET>","grant_type":"client_credentials"}'
```

Ждём `{"access_token":"...","expires_in":1800,"token_type":"Bearer"}`.

---

## 2. Ключи Seller API (остатки и аналитика)

1. Личный кабинет → **Настройки → Seller API**
2. **Сгенерировать ключ**
3. Название + **уровень доступа** — минимальный, покрывающий аналитику и остатки
4. Цель использования — «для личного пользования»
5. **Сгенерировать**

`Client-Id` — на этой же странице рядом с ключами, это число.

Три предупреждения из документации Ozon, все существенные:

- **Ключ показывается один раз, при создании.** Не сохранили — восстановить нельзя,
  только выпускать новый.
- **Срок действия 3 месяца.** Через 90 дней Seller-вызовы начнут падать. Дата
  истечения доступна методом `/v1/roles` в поле `expires_at` — ротацию можно
  поставить на таймер, не дожидаясь аварии.
- Если оферта неактуальна, Seller API ответит `403 Offer not signed`. Сначала
  принять оферту в кабинете.

## 3. Завести магазин в сервере

Веб-интерфейс сервера → `/shops` → добавить магазин. Поля обеих секций заполняются
**разными** парами из § 1 и § 2.

`shop_id` — короткий идентификатор латиницей, он же будет привязан к токену клиента
в § 4. Менять его потом больно: он попадает в токены и в статистику.

---

## 4. Выдать клиенту личный токен

Токен здесь — не пропуск, а удостоверение: он жёстко привязан к одному магазину, и
`shop_id` из аргументов подставляется принудительно. Подробности — `FORK.md`.

```bash
openssl rand -hex 32
```

Полученное значение добавить в `MCP_CLIENT_TOKENS` через запятую:

```
MCP_CLIENT_TOKENS=<токен1>:<shop_id1>,<токен2>:<shop_id2>
```

Переменная живёт в `.env` рядом с `docker-compose.yml`. Применить:

```bash
docker compose up -d ozon-mcp
```

> ⚠️ Именно `up -d`, а не `restart`: перезапуск новую переменную окружения **не
> подхватывает**, и снаружи это выглядит как «токен не работает».

> ⚠️ Как только задан хоть один клиентский токен, общий `MCP_AUTH_TOKEN`
> **перестаёт пускать**. Так задумано: он не привязан к магазину и остался бы обходом.

Клиент подключается к `<host>/sse` с заголовком `Authorization: Bearer <его токен>`.

### 4.1. Куда этот порт нельзя выставлять

🔴 **Токен проверяют только `/sse` и `/messages`. Веб-интерфейс открыт целиком.**
Проверено 2026-09-18: `GET /shops` отдаёт `200` без всякого токена, тогда как
`GET /sse` — `401`.

Без токена доступны, в частности:

- `GET /shops` — список магазинов и ключи в замаскированном виде;
- `POST /api/shops` — **завести магазин**, `DELETE /api/shops/{id}` — **удалить**;
- `GET /api/stats`, `GET /` — статистика вызовов **всех** арендаторов;
- `POST /api/diagnostics/run` — прогон диагностики.

Привязка клиента к магазину этого не закрывает и не пытается: она про MCP-сессию,
а не про админку. Поэтому порт сервера **не выставлять наружу**: слушать на
`127.0.0.1` и ходить через обратный прокси с собственной авторизацией, либо держать
в закрытом контуре. Иначе изоляция арендаторов теряет смысл — сосед не станет
подбирать `shop_id`, он просто откроет `/shops`.

## 5. Приёмка

Не «сервер поднялся», а «оно отвечает по этому продавцу». Четыре проверки, каждая
отвечает на свой вопрос. **Пустой или неясный результат читать как «не проверено».**

**5.1. Сервер жив**

```bash
curl -sS -o /dev/null -w 'http=%{http_code}\n' http://127.0.0.1:8765/api/health
```

**5.2. Каталог урезан, как задумано.** При `OZON_TOOLSETS=ads,analytics` клиент видит
**41** инструмент, и `shop_id` не должен встречаться ни в одной схеме — иначе модели
предлагается выбор, которого у неё нет.

**5.3. Обе пары ключей рабочие.** У сервера для этого есть встроенная проверка: она
дёргает по одному реальному методу каждого API и отвечает раздельно.

```bash
curl -sS -X POST http://127.0.0.1:8765/api/shops/<shop_id>/test
```

Ждём `{"seller_ok":true,"perf_ok":true,"errors":[]}`. **Оба поля обязаны быть `true`**
— именно эта проверка ловит подмену пар из § 0, потому что различает, какой из двух
API отказал:

| Что в ответе | Причина |
|---|---|
| `perf_ok:false`, `401 invalid_client` | Performance-пара неверна или `client_id` в короткой форме |
| `seller_ok:false`, `400 ... positive integer` | в Seller-секцию вписана Performance-пара |
| `seller_ok:false`, `403 Offer not signed` | не принята оферта в кабинете |
| `429 Too Many Requests` | уткнулись в лимит Ozon, подождать и повторить |
| `ConnectTimeout` | сеть; см. § 6 |

**5.4. Ассистент действительно получает данные.** Проверка из 5.3 ходит в Ozon мимо
MCP — она говорит про ключи, но не про то, что путь до клиента цел. Вызвать
`ozon_ad_campaigns` без аргументов и увидеть `{"list":[...],"total":N}`.

**5.5. Изоляция держится.** Обязательна, если на сервере больше одного продавца.
Вызвать `ozon_ad_campaigns` дважды токеном одного клиента: без аргументов и с
`shop_id` соседа. **Ответы обязаны совпасть** — значит чужой идентификатор ни на что
не влияет. Расхождение или данные соседа = утечка, сервер в таком виде не запускать.

## 6. Если ничего не отвечает

Перед тем как искать причину в ключах — проверить сеть. Ozon отдаёт `401` на
неавторизованный запрос за доли секунды, и это признак исправного канала:

```bash
curl -sS -o /dev/null -w 'http=%{http_code} connect=%{time_connect}s\n' -m 15 \
  -X POST https://api-performance.ozon.ru/api/client/token \
  -H 'Content-Type: application/json' -d '{"grant_type":"client_credentials"}'
```

- `http=401`, `connect` в районе реального RTT — канал в порядке, причина в ключах.
- Таймаут или зависание на TLS-хендшейке — канал. **Первым делом выключить VPN:**
  2026-09-18 туннель с MTU 1000 ронял хендшейк ко всем хостам Ozon, при том что
  `pypi.org` открывался. Выглядело как блокировка по гео и ею не было.
- `connect` в 1–2 мс до удалённого хоста — соединение терминируется локально
  (VPN, прокси, сетевой стек Docker Desktop). Такому замеру верить нельзя, мерить
  надо с хоста.

## 7. Лимиты Ozon

Считаются на аккаунт продавца, поэтому на нескольких продавцов **не складываются**.

| Лимит | Значение |
|---|---|
| Всего запросов | 100 000 в сутки |
| Изменение ставок | 6 000 в день, **500 в час** |
| Изменение бюджета и стратегии | 500 в день, **100 в час** |
| Создание кампаний | 1 000 в день, 300 в час |
| Добавление товаров в кампанию | 1 200 в день (≤1000 за раз), 200 в час |

Упирается автоматика обычно в **часовой** лимит, а не в суточный.

- `GetProductPlacementZoneInfo` (зоны размещения товара) — в сервере не реализован.
